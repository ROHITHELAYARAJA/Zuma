ABDM mock deployment

Use only the repository fixtures. This is a local happy-path mock, not the live ABDM sandbox. Consent is automatically granted, gateway context is in memory, and the gateway uses v0.5. Set wrapper profile v1. The gateway coordinates exchange; clinical payloads are pushed to the HIU receiver by the HIP flow.

1. Start locally

Start Docker's Linux engine. From the project folder:

npm install
npm run abdm:data
npm run abdm:up

After the Java images build, use PowerShell:

$env:ABDM_MOCK_ENABLED="true"
npm run abdm:flow

The runner uses current dates and returned consent IDs. A receipt is saved under data/abdm/transfers only when decrypted entries arrive. Inspect failures with docker compose -f infrastructure/abdm/compose.yaml logs --tail 80.

2. Supabase

  1. Open the project's SQL Editor.
  2. Run deployment/supabase-complete.sql.
  3. Run deployment/abdm-repository-data.sql. It preserves both original FHIR bundles, raw partial birth dates, source commit and SHA256 in abdm_repository_reports.
  4. Create a doctor in Authentication, then add its UUID to clinician_memberships with hospital_id B, role doctor, active true.

The connected account currently denies access to the supplied Supabase project. No remote tables or data have been changed. Supabase is for app identity and clinical data. The upstream Java wrapper still requires MongoDB for its internal workflow state.

3. Prepare the GitHub upload

The project is initialized with Git. Upload it including vendor/ABDM-wrapper and its license, excluding node_modules, environment secrets, databases and transfer receipts. The upstream source is pinned in data/abdm/dataset.json. Local changes provide container builds and configurable gateway callback routing.

5. Render: existing clinical API

New → Web Service. Name clinical-api; Node runtime; application root directory. Build: npm ci --include=dev. Start: npm start. Health check: /api/health. Import deployment/render-clinical-api.env.example, then set Supabase's server credential on Render only.

The old Node hospital transport and the Java ABDM transport have different APIs. Do not replace HOSPITAL_A_API_URL with a Java HIP URL. The original /workspace remains the generated Ravi demo. The new /abdm workspace uses protected report-specific consent, source verification, Python Bedrock answers, clinician approval and export. It keeps the two repository patients separate.

6. AWS retrieval dataset

data/abdm/evidence has two HTML evidence documents and managed knowledge-base metadata files. data/abdm/evaluation.json contains text and voice grounding checks. This updates retrieval evidence, not model weights. Both input modes should use the same authorized evidence.

  1. Create a separate demonstration KB and connect its S3 evidence/ prefix.
  2. Set AWS_CLOUD_ENABLED=true, AWS_REGION, credentials, S3_REPORT_BUCKET, S3_KMS_KEY_ID, BEDROCK_KNOWLEDGE_BASE_ID, BEDROCK_DATA_SOURCE_ID, BEDROCK_KB_MODE=managed and ABDM_KB_DATASET=nha-abdm-repository.
  3. Run npm run abdm:upload -- --apply, then check ingestion status.

Keep this dataset separate from the original demo KB. Use /abdm for these repository report IDs. Its Python adapter applies patient/report/hash filters and checks source hashes, then returns only exact source facts selected by the model. The original /workspace has a separate allowlist. Terminology in the source bundles requires review before clinical use.

7. Vercel manual deployment

  1. Add New Project → import the GitHub repository.
  2. Select Next.js. Root Directory is the folder containing package.json.
  3. Import deployment/vercel.env.example. Set API_PROXY_TARGET to the clinical API's HTTPS URL.
  4. Deploy. Copy the final Vercel origin into APP_ORIGINS on Render and redeploy the clinical API.
  5. Open /abdm for repository fixtures, /setup for platform configuration, and /workspace for the separately labelled older clinical demo.

No Vercel deployment was performed. Do not put AWS credentials or Supabase's server credential in NEXT_PUBLIC variables.

Deploy the Python AWS service

Create a Render Private Service named zuma-aws-evidence in the same region as zuma-clinical-api. Runtime Python; repository root; build pip install .; start uvicorn zuma_aws.service:app --host 0.0.0.0 --port 8795. Import deployment/python-aws.env locally through Render Environment. It contains secrets: do not commit or share it. The blueprint infrastructure/render-python.yaml contains only placeholders.

Copy the Python service Internal Address into RAG_SERVICE_URL on zuma-clinical-api, prefixed with http:// and including port 8795. Set the same RAG_SERVICE_API_KEY on both services. Import the updated deployment/clinical-api.env on the clinical API. Open /abdm, sign in, grant the report demonstration permission and ask a question. Do not put the Python service key or AWS credentials on Vercel.

Text retrieval, permission grant/revocation, and end-to-end voice input to cited answer to speech have been tested live. Voice input uses the Nova 2 Sonic bidirectional SDK. The same evidence-answer function handles its transcript. Output defaults to Amazon Polly reading the selected source text, because native Nova speech can add unsourced advice. Native nova-strict output remains optional and is withheld if its caption does not match. The microphone accepts at most 20 seconds, 16 kHz mono PCM. Both text and voice use the same source-restricted answering function.
